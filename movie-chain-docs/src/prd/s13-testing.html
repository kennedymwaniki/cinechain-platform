13Testing Strategy

Two categories of test in this system are not optional and cannot be approximated: isolation tests and concurrency tests. Everything else is ordinary.

13.1 The isolation suite

This suite exists to answer one question with evidence rather than confidence: can tenant A reach tenant B's data by any route? It runs against a real PostgreSQL via Testcontainers, because RLS cannot be exercised against a mock.

The test every endpoint must pass
GIVEN  tenant A and tenant B both exist, each with a booking
WHEN   a user of tenant A calls every endpoint in the catalogue,
       substituting tenant B's resource identifiers
THEN   every response is 404 — never 403, never 200, never a
       timing difference large enough to distinguish the two

AND    the attempt is recorded as a security event
AND    no row belonging to B appears in any response body

This is generated rather than hand-written: the suite enumerates the route table, so a new endpoint is covered the day it is added. An endpoint that cannot be exercised this way must be explicitly annotated as public, and that annotation is reviewed.

Proving RLS itself works — run this in CI, not just once
-- 1 · The policy blocks reads
SET LOCAL app.tenant_id = 'aaaa-...-a';
SELECT count(*) FROM booking;          -- expect: only A's rows

SET LOCAL app.tenant_id = 'bbbb-...-b';
SELECT count(*) FROM booking;          -- expect: only B's rows

-- 2 · Unset tenant returns NOTHING, not everything. Fail closed.
RESET app.tenant_id;
SELECT count(*) FROM booking;          -- expect: 0

-- 3 · WITH CHECK blocks writing a foreign tenant_id
SET LOCAL app.tenant_id = 'aaaa-...-a';
INSERT INTO booking (tenant_id, ...) VALUES ('bbbb-...-b', ...);
-- expect: ERROR — new row violates row-level security policy

-- 4 · The application role cannot bypass RLS
SELECT rolbypassrls FROM pg_roles WHERE rolname = 'cinechain_app';
-- expect: false     ← this single assertion catches the classic mistake

-- 5 · The platform consumer directory is unreachable from tenant code.
--     platform.consumer has NO RLS policy (§6.2), so its protection is
--     the grant, not a policy. Assert the grant, or the exception
--     becomes a hole nobody notices.
SET LOCAL app.tenant_id = 'aaaa-...-a';
SELECT * FROM platform.consumer;
-- expect: ERROR — permission denied for table consumer

Token-type tests

§4.2 splits users into three populations. Three assertions keep that split honest, and they belong in the generated suite alongside the cross-tenant probes.

GIVEN  a staff token for tenant A
WHEN   it is presented to a consumer endpoint (POST /screenings/:id/holds)
THEN   403 wrong_token_type — a Nyati clerk must not transact as a
       Prestige customer

GIVEN  a consumer token (no tenant_id claim)
WHEN   it is presented to a staff endpoint (POST /theatres)
THEN   401 no_tenant_context — never defaulted to any tenant

GIVEN  a hold_token minted for a screening belonging to tenant A
WHEN   it is replayed against a booking for tenant B's screening
THEN   401 hold_token_invalid — the tenant is inside the signature
Test 4 is the one that matters most

Every other test in this suite passes happily against a database where the application connects as the table owner — because the owner bypasses RLS and sees everything, including the rows the test expects. Asserting rolbypassrls = false, and that the application role is not the table owner, is what makes the rest of the suite meaningful. Without it, a green test run proves nothing.

13.2 Concurrency tests

These target the guarantees in §7.1. They must run against real Redis and real PostgreSQL; in-memory substitutes do not reproduce the interleavings that matter.

13.3 Load profile

The load test must reproduce the skew, not merely the volume. A uniformly distributed 800 requests per second tells you almost nothing about how this system behaves in production.

k6 scenario — the blockbuster on-sale
Tenant NYATI      95% of load · 760 rps · one screening · 240 seats
Tenants OTHERS     5% of load ·  40 rps · ordinary browsing

Ramp: 0 → 800 rps over 30 s, hold 5 min, drop to 50 rps

Pass criteria
  · other tenants' p95 latency degrades by  < 20%     ← the real test
  · zero double sales
  · hold acquisition p99 < 400 ms for ALL tenants
  · 429s are returned to NYATI, not errors to everyone else

The first criterion is the one that matters. A system that survives the peak by making every tenant slow has not passed — it has merely failed evenly.
