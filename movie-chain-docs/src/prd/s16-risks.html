16.2 Resolved — customer identity

An earlier draft of this document listed “can one person hold accounts at two chains with the same e-mail?” as an open question, and answered it in the body by saying such a customer would simply register twice. That answer was wrong, and the reasoning behind it was wrong.

What the earlier draft got wrong, and why it matters

It claimed that linking a customer's identities across chains would create the very cross-tenant join the architecture exists to prevent. It would not. The link is safe precisely because platform.consumer sits outside the tenant boundary and no tenant-scoped query can reach it (§6.2).

The practical cost of the earlier position was worse than the duplicated registration it accepted: a customer of Nyati travelling to a town served only by Prestige would have been unable to book at all, because their token asserted a tenant they were not transacting with.

Resolved: one global consumer identity, carrying no tenant claim; guest checkout as the primary path; per-chain loyalty on tenant_customer. Specified in §4.2, §5.0 and §6.2.

16.3 Open questions

These require a decision from outside the engineering team. Each is listed with the consequence of deciding late.

QuestionNeeded byWhy it cannot drift
Should guest bookings expire from the platform consumer directory if never converted?Before P2 endsA guest who never registers leaves a tenant_customer row with no consumer_id. Retention of those rows is a data-protection question, not a technical one.

Is 5 minutes the right hold window for M-Pesa?Validate in P2M-Pesa requires handset confirmation. If the real distribution is longer, the default must move before launch.
Do chains want to share a film catalogue, or curate their own?Before P1 endsCurrently film is tenant-scoped. A shared catalogue would introduce a genuinely global table, which is a deliberate hole in the isolation model and needs designing rather than discovering.
Is seat-gap prevention (FR-47) commercially important?ResolvedYes on sell-out nights, no on quiet ones. Demand drives it: the rule activates above a per-tenant occupancy threshold, as a pure pre-check before the atomic acquire, so the hold algorithm itself is unchanged (implementation plan, step 13).
On the film catalogue question

It is worth flagging because it is the only place in this design where a global, cross-tenant table is plausibly correct. Films are objectively the same object for every chain: Avengers: Doomsday has one runtime and one certificate regardless of who screens it.

If that path is taken, the right shape is a global film_catalogue that is read-only to tenants, with a tenant-scoped film record referencing it for pricing and local metadata. What must be avoided is a shared table that tenants can write to — that is a cross-tenant write path, and it would be the single weakest point in an otherwise strict model.

16.4 Appendix — the isolation checklist

Extracted for use in code review. If a change touches data access, it should be walked through.

  • Tenant identity comes from the verified token for staff, and from the resource for consumers — never from a caller-supplied tenant value.
  • A consumer token cannot reach a staff endpoint, and a staff token cannot reach a consumer endpoint. Both are 403 and logged.
  • consumer_id is never returned to a tenant, and no tenant-scoped query joins to platform.consumer.
  • A missing tenant claim results in rejection, never a default.
  • A tenant named in the URL is validated against the token, and a mismatch returns 404.
  • The table has tenant_id, RLS enabled, FORCEd, and both USING and WITH CHECK.
  • The connection is obtained through the single tenancy provider, and SET LOCAL runs on that same connection.
  • The application role is not the table owner and does not have BYPASSRLS.
  • Cache keys, queue names and storage paths carry the tenant prefix.
  • Background jobs set tenant context from their payload before touching data.
  • Any job that deliberately runs platform-wide is one of the two approved exceptions.
  • Errors do not disclose the existence of another tenant's resources.
  • Logs carry the tenant label and no personal data.
