6Domain and Data Design

The schema is the most durable artefact in this project. Everything in this section is technology-neutral PostgreSQL and applies identically to both editions of this document.

6.1 The tenancy columns

Two rules govern every table in the application plane, and they are not negotiable:

  1. The table carries a tenant_id uuid NOT NULL column.
  2. Row-level security is enabled on the table with an isolation policy, and the application role cannot bypass it.

Rule 1 attracts an objection worth answering. seat already links to screen, which links to theatre, which carries tenant_id — so storing it again on seat is denormalised. That is true and it is the right trade. Without the column on every table, a row-level policy on seat would have to join three tables to evaluate, which is both slow and fragile. The denormalisation buys an independent, cheap, locally-evaluable security policy on every table. It is the single most valuable duplicate column in the schema.

Tenant registry — control plane
CREATE TYPE tenant_tier AS ENUM ('basic', 'standard', 'premium', 'dedicated');
CREATE TYPE tenant_status AS ENUM ('pending','provisioning','active','suspended','offboarding');

CREATE TABLE tenant (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  slug          text NOT NULL UNIQUE,          -- 'nyati' -> nyati.cinechain.app
  name          text NOT NULL,
  tier          tenant_tier   NOT NULL DEFAULT 'basic',
  status        tenant_status NOT NULL DEFAULT 'pending',
  country       char(2) NOT NULL DEFAULT 'KE',
  -- where this tenant's data lives; NULL means the shared pool
  db_ref        text,
  hold_seconds  int  NOT NULL DEFAULT 300 CHECK (hold_seconds BETWEEN 120 AND 900),
  max_seats_per_booking int NOT NULL DEFAULT 10,
  created_at    timestamptz NOT NULL DEFAULT now()
);

Note db_ref. This single nullable column is what allows a tenant to be promoted from the pooled database to a dedicated one without any application change: the connection resolver reads it, and everything downstream is identical.

6.2 Identity — two tables on opposite sides of the boundary

This is where §4.2's three populations become schema. Staff are tenant-scoped and behave like every other tenant table. Consumers are not, and must not be.

Staff — tenant-scoped, RLS applies
-- Formerly 'app_user'. Renamed so the distinction is unmissable.
CREATE TABLE staff_user (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  uuid NOT NULL,          -- always present; never null
  email      citext NOT NULL,
  role       text NOT NULL,           -- box_office | theatre_manager | chain_admin
  theatre_id uuid,                     -- null = whole chain
  status     text NOT NULL DEFAULT 'active',
  -- unique WITHIN a chain: the same person may work for two chains,
  -- and gets a separate account at each. That is correct — see §4.2.
  UNIQUE (tenant_id, email)
);
Consumers — platform-level, OUTSIDE the tenant boundary
CREATE SCHEMA platform;

-- No tenant_id. No RLS policy. Not in the RLS loop in §6.5.
-- Reachable ONLY through the identity service, never from a
-- tenant-scoped query. This is a deliberate exception (see below).
CREATE TABLE platform.consumer (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email        citext NOT NULL UNIQUE,   -- one person, one account, globally
  phone        text,
  display_name text,
  status       text NOT NULL DEFAULT 'active',
  created_at   timestamptz NOT NULL DEFAULT now()
);

-- The per-chain projection: what THIS chain knows about a customer,
-- because that customer transacted with THIS chain. Fully RLS-guarded.
CREATE TABLE tenant_customer (
  tenant_id      uuid NOT NULL,
  consumer_id    uuid,                  -- NULL for guest purchases
  email          citext NOT NULL,
  display_name   text,
  loyalty_points int NOT NULL DEFAULT 0,
  first_seen_at  timestamptz NOT NULL DEFAULT now(),
  -- keyed on email so a guest who later registers is linked (FR-77)
  PRIMARY KEY (tenant_id, email)
);
Why this satisfies both FR-75 and FR-79

FR-75 — Grace books anywhere. Her token carries a consumer id and no tenant claim, so nothing scopes her to a chain. The tenant of each purchase is derived from the screening she chose.

FR-79 — no chain can see she uses another. A chain reads tenant_customer, which RLS scopes to its own rows. platform.consumer is not in the RLS loop because it is not reachable from tenant-scoped code at all — a different database role and a different service own it. There is no query a chain can write that crosses from their row to another chain's.

The deliberate exception, named so it cannot be forgotten

platform.consumer is a cross-tenant table in an otherwise strict model. Alongside the sweeper and the metering aggregator (§12.5), it is one of the few places that deliberately sits outside tenant isolation. It must therefore be: reachable through exactly one service, never joined to from application-plane code, covered by a test asserting a tenant-scoped connection cannot read it, and reviewed as security-sensitive.

A practical corollary for the API layer: never return consumer_id to a tenant. It is an internal join key. The same opaque identifier visible to two chains is exactly the raw material for the correlation FR-79 forbids.

6.3 Application-plane tables

Venue hierarchy
CREATE TABLE theatre (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  uuid NOT NULL,
  name       text NOT NULL,
  city       text NOT NULL,
  timezone   text NOT NULL DEFAULT 'Africa/Nairobi',
  -- names unique WITHIN a tenant, never globally
  UNIQUE (tenant_id, name)
);

CREATE TABLE screen (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  uuid NOT NULL,
  theatre_id uuid NOT NULL REFERENCES theatre(id) ON DELETE RESTRICT,
  name       text NOT NULL,
  format     text NOT NULL DEFAULT 'standard',
  UNIQUE (tenant_id, theatre_id, name)
);

CREATE TABLE seat (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  uuid NOT NULL,
  screen_id  uuid NOT NULL REFERENCES screen(id) ON DELETE RESTRICT,
  row_label  text NOT NULL,              -- 'A', 'B', 'AA'
  seat_number int NOT NULL,
  seat_class text NOT NULL DEFAULT 'standard',
  is_active  boolean NOT NULL DEFAULT true,   -- false = removed / aisle gap
  UNIQUE (screen_id, row_label, seat_number)
);
Catalogue and scheduling
CREATE TABLE film (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id   uuid NOT NULL,
  title       text NOT NULL,
  runtime_min int  NOT NULL CHECK (runtime_min BETWEEN 1 AND 600),
  rating      text, language text, poster_url text,
  release_date date
);

CREATE TYPE screening_status AS ENUM
  ('draft','published','closed','completed','cancelled');

CREATE TABLE screening (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  uuid NOT NULL,
  screen_id  uuid NOT NULL REFERENCES screen(id),
  film_id    uuid NOT NULL REFERENCES film(id),
  starts_at  timestamptz NOT NULL,
  ends_at    timestamptz NOT NULL,
  base_price_minor int NOT NULL,          -- cents; never floats for money
  currency   char(3) NOT NULL DEFAULT 'KES',
  status     screening_status NOT NULL DEFAULT 'draft',
  CHECK (ends_at > starts_at)
);

-- FR-22: the database itself refuses overlapping screenings on one screen.
-- Application-level checks race; an exclusion constraint cannot.
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE screening ADD CONSTRAINT no_screen_overlap
  EXCLUDE USING gist (
    screen_id WITH =,
    tstzrange(starts_at, ends_at + interval '20 minutes') WITH &&
  ) WHERE (status <> 'cancelled');
Why the exclusion constraint matters

FR-22 says overlapping screenings must be rejected. The obvious implementation — query for conflicts, then insert if none — is the same check-then-act race described in §7.2. Two managers scheduling simultaneously can both see no conflict and both insert.

The exclusion constraint makes the guarantee structural. It is the same principle as the seat lock, applied to a different resource: collapse the check and the act into one operation the database guarantees is indivisible.

6.4 The seat lock table

This is the table the entire booking flow turns on. One row represents one seat at one screening.

Seat locks, bookings and tickets
CREATE TYPE lock_status AS ENUM ('held', 'sold');

CREATE TABLE seat_lock (
  screening_id uuid NOT NULL REFERENCES screening(id) ON DELETE CASCADE,
  seat_id      uuid NOT NULL REFERENCES seat(id),
  tenant_id    uuid NOT NULL,
  status       lock_status NOT NULL,
  hold_id      uuid,                    -- who owns the hold
  expires_at   timestamptz,             -- NULL once sold
  booking_id   uuid,
  created_at   timestamptz NOT NULL DEFAULT now(),
  -- THE guarantee: one seat, one screening, one row. Cannot be violated.
  PRIMARY KEY (screening_id, seat_id),
  CHECK (status = 'sold' OR expires_at IS NOT NULL)
);

CREATE TYPE booking_status AS ENUM
  ('pending','confirmed','cancelled','refunded','expired');

CREATE TABLE booking (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id    uuid NOT NULL,
  screening_id uuid NOT NULL REFERENCES screening(id),
  -- who bought it. consumer_id is NULL for guest purchases (FR-70);
  -- the contact details are captured at payment either way and are
  -- the immutable record of the transaction.
  consumer_id  uuid,
  guest_email  citext NOT NULL,
  guest_name   text NOT NULL,
  guest_phone  text,
  status       booking_status NOT NULL DEFAULT 'pending',
  total_minor  int NOT NULL,
  currency     char(3) NOT NULL DEFAULT 'KES',
  reference    text NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  -- unique WITHIN the tenant: two chains may both issue 'NYT-4471'
  UNIQUE (tenant_id, reference)
);

CREATE TABLE ticket (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id   uuid NOT NULL,
  booking_id  uuid NOT NULL REFERENCES booking(id) ON DELETE CASCADE,
  seat_id     uuid NOT NULL REFERENCES seat(id),
  price_minor int  NOT NULL,          -- captured at purchase, never recomputed
  code_hash   text NOT NULL UNIQUE,   -- store the hash, not the code
  redeemed_at timestamptz,
  redeemed_by uuid
);

6.5 Isolation policy

The policyPostgreSQL — CREATE POLICYCrunchy Data — RLS for tenants is mechanical and identical on every tenant-scoped table, which means it should be generated rather than hand-written.

Row-level security
-- The application connects as this role. It is NOT the table owner,
-- and it does NOT have BYPASSRLS. Both matter: owners bypass policies.
CREATE ROLE cinechain_app LOGIN;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO cinechain_app;

DO $$
DECLARE t text;
BEGIN
  FOREACH t IN ARRAY ARRAY[
    'theatre','screen','seat','film','screening',
    'seat_lock','booking','ticket','payment','pricing_rule',
    'staff_user','tenant_customer'   -- NOT platform.consumer: see 6.2
  ] LOOP
    EXECUTE format('ALTER TABLE %I ENABLE ROW LEVEL SECURITY', t);
    -- FORCE applies the policy to the table owner too
    EXECUTE format('ALTER TABLE %I FORCE ROW LEVEL SECURITY', t);
    EXECUTE format($f$
      CREATE POLICY tenant_isolation ON %I
        USING      (tenant_id = current_setting('app.tenant_id', true)::uuid)
        WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid)
    $f$, t);
  END LOOP;
END $$;
Three details that decide whether this actually works

WITH CHECK as well as USING. USING governs what you can read; WITH CHECK governs what you can write. Without it, a tenant could insert a row stamped with another tenant's id — invisible to them afterwards, but present, and a route to corrupting another tenant's data.

FORCE ROW LEVEL SECURITY. Without FORCE, the table owner bypasses the policy silently. Many teams enable RLS, run their tests as the owner, see everything pass, and ship a policy that has never been exercised.

current_setting('app.tenant_id', true)PostgreSQL — SET / SET LOCAL. The second argument makes a missing setting return NULL rather than raising. Since NULL = anything is never true, an unset tenant yields zero rows rather than an error — the system fails closed. Set it with SET LOCAL inside the transaction, never plain SET, or a pooled connection will carry one tenant's value into the next tenant's request.

6.6 Indexing

In a pooled schema, an indexCitus — Multi-tenant applications that does not lead with tenant_id forces the database to scan across tenants and discard rows. This is correct, invisible in development with three tenants, and progressively ruinous.

Indexes
-- tenant_id leads every composite index on a tenant-scoped table
CREATE INDEX ON screening (tenant_id, screen_id, starts_at);
CREATE INDEX ON screening (tenant_id, film_id, starts_at)
  WHERE status = 'published';      -- partial: browsing only wants published
CREATE INDEX ON booking   (tenant_id, guest_email, created_at DESC);
-- a consumer's cross-chain history: scoped by person, NOT by tenant,
-- so this one deliberately does not lead with tenant_id (FR-76)
CREATE INDEX ON booking   (consumer_id, created_at DESC) WHERE consumer_id IS NOT NULL;
CREATE INDEX ON seat      (tenant_id, screen_id) WHERE is_active;

-- the hot path: "give me the whole seat map for this screening"
CREATE INDEX ON seat_lock (screening_id) INCLUDE (seat_id, status, expires_at);

-- the sweeper's query; partial index keeps it tiny
CREATE INDEX ON seat_lock (expires_at) WHERE status = 'held';

6.7 Decision record — how tenant data is partitioned

This is the decision with the longest shadow in the project. It is recorded here in full, with the options that were rejected and the evidence for each, so that it can be reviewed rather than inherited.

ADR-001 — Tenant data partitioningAccepted · supersedes nothing
Context

CineChain must serve a long tail of small cinemas at a price point they will accept, while also being able to sign a national chain whose contract may demand dedicated infrastructure. These two requirements pull in opposite directions, and the partitioning model is where that tension is resolved. The decision must be made before the first migration, because it cannot be changed cheaply afterwards.

Options considered

Option A — shared tables with a tenant_id discriminator. All tenants' rows in one set of tables, separated by a column and enforced by row-level security. This is what Golding calls pooled relational partitioning: take the existing design and introduce a tenant identifier that becomes the leading index, with the former primary key demoted to secondary.G ch. 8, “Pooled Relational Data Partitioning”, p. 200

Option B — one database, a schema per tenant. Identical tables repeated inside nyati, prestige, sarit schemas; the tenant chosen by setting search_path per request.

Option C — a database per tenant. Physically separate databases, chosen when the connection is opened. Golding notes relational silos come in three grades — instance, database, or table per tenant — and that engine limits should inform which.G ch. 8, “Siloed Relational Data Partitioning”, pp. 201–202

Evaluation against our actual requirements

Decision

Adopt Option A as the default for every table, with row-level security as the enforcing mechanism. Provide Option C for individual tenants on the Premium and Dedicated tiers, selected by configuration. Reject Option B entirely.

Option B is rejected because its costs scale with tenant count in the same way C's do — migrations run once per schema — while its blast radius remains shared like A's. It would buy most of C's operational burden for only part of C's isolation benefit. It remains available if a future requirement specifically needs per-tenant dump and restore without physical separation, but nothing in the current requirements asks for that.

The default follows the book's guidance directly:

“My recommendation is to default to a pooled model for all the storage in your system… you're essentially forcing any siloed data to earn its way out based on a set of clear requirements that justify taking on the trade-offs.”

— Golding, ch. 8, “Defaulting to a Pooled Model”, p. 195

What qualifies a tenant to move to Option C

A tenant moves to a dedicated database when, and only when, one of these is true. Revenue and customer prominence are not on this list — those are reasons to price a silo, not to need one.

  • A contract or regulator requires physical separation or data residency in a named jurisdiction.
  • The tenant must supply and control their own encryption key.
  • Their data volume measurably degrades shared index performance for other tenants.
  • They require a recovery or retention guarantee that shared storage cannot meet.
Consequences — accepted
  • Row-level security becomes load-bearing. In Option A a forgotten predicate is a data breach rather than a bug. RLS is therefore not defence in depth here — it is the primary control, and §13.1 tests it as such.
  • Every index must lead with tenant_id. Enforced in the definition of done (§15.2).
  • Uniqueness is composite. (tenant_id, reference), never reference alone.
  • A tenant-deletion job must be written and tested early, because Option A cannot satisfy FR-8 by dropping anything.
  • Siloed tenants keep the tenant_id column even though it is constant for them — so that the schema, the queries and the policies are byte-identical in both models.
  • Connection state must be transaction-scoped. SET LOCAL, never SET, or pooling leaks one tenant's context into the next request.
How we keep the escape hatch cheap

The decision is only safe if moving a tenant from A to C stays a configuration change. Three properties guarantee it, and all three are testable:

  1. The schema is identical in both models — same migrations, same policies, same tenant_id column.
  2. Placement is a data lookup: tenant.db_ref, null meaning the shared pool, read by the connection resolver at the edge of each request.
  3. No business logic branches on tier or placement. Enforced in review (§10.2).

The migration procedure itself is specified in §10.3.

Revisit this decision when
  • Any single tenant exceeds roughly 15% of total row volume in seat_lock or ticket.
  • More than a quarter of tenants qualify for Option C — at which point the pooled default is no longer serving the majority.
  • Native table partitioning by tenant_id stops containing the largest tenants (see the growth table in §6.5).
  • A market is entered whose data-residency rules apply to all customers rather than a few.
