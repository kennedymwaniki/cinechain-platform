14.3 Runbooks

A customer says a seat shows as taken but the cinema is empty
Almost always a stranded hold. Check Redis for the key and seat_lock for a row past expires_at. If the durable row persists with no Redis key, the sweeper has stalled — check its leader election. Resolve by deleting the specific lock row; never by flushing Redis, which would drop every live hold across all tenants.
One tenant is degrading the platform
Confirm with per-tenant request rate and latency. Tighten that tenant's ingress rate limit first — it takes effect in seconds and protects everyone else immediately. Then scale Inventory. If this recurs, the tenant belongs on Premium with a dedicated database, and that is a commercial conversation rather than an engineering one.
A tenant reports seeing another tenant's data
Treat as a security incident from the first minute. Capture the request identifier and the exact response. Verify RLS is enabled and FORCEd on the table in question, and that the application role still has rolbypassrls = false — a migration run as the owner can silently change this. Do not deploy a fix before establishing the blast radius: which tenants, which rows, over what period.
Payment provider outage during an on-sale
Extend hold windows platform-wide via configuration so customers mid-flow are not penalised. Display a banner. Do not retry captures blindly — use the idempotency key and poll for the true status, or you will double-charge on recovery.
Promoting a tenant from pooled to siloed
Follow §10.3. The two steps to not skip: verify row counts and checksums before cutover, and retain the source rows afterwards so the change is reversible for a defined window.
