12.1 Tenant context

The store is a module-level singleton. Nothing outside tenancy/ imports it directly; consumers use the accessor, which throws rather than returning a default.

tenancy/tenant-context.ts
import { AsyncLocalStorage } from 'node:async_hooks';

export type TenantId = string & { readonly __brand: 'TenantId' };

export interface TenantContext {
  tenantId: TenantId;
  tier: 'basic' | 'standard' | 'premium' | 'dedicated';
  userId: string;
  role: string;
  holdSeconds: number;
}

const als = new AsyncLocalStorage<TenantContext>();

export const runWithTenant = <T>(ctx: TenantContext, fn: () => T) =>
  als.run(ctx, fn);

/** Throws rather than returning undefined. A missing tenant is a bug,
 *  never a case to handle gracefully — fail closed, loudly. */
export function currentTenant(): TenantContext {
  const ctx = als.getStore();
  if (!ctx) throw new Error(
    'No tenant context. Code ran outside a tenant-scoped request — ' +
    'if this is a worker, call runWithTenant() from the job payload.'
  );
  return ctx;
}
tenancy/tenant.interceptor.ts — the most important class in the codebase
@Injectable()
export class TenantContextInterceptor implements NestInterceptor {
  constructor(private tenants: TenantRegistry, private db: TenantDb) {}

  async intercept(exec: ExecutionContext, next: CallHandler) {
    const req = exec.switchToHttp().getRequest();
    const claims = req.user;                // set by JwtAuthGuard

    // 1 · ONLY from the verified token. Never a header, path or body.
    //     This interceptor guards STAFF endpoints only — a consumer
    //     token legitimately has no tenant claim (§4.2), and reaches
    //     the application through ConsumerGuard instead.
    const tenantId = claims?.tenant_id as TenantId | undefined;
    if (!tenantId) throw new UnauthorizedException('no_tenant_context');

    // 2 · If the path also names a tenant, a mismatch is an attack.
    const hinted = req.params?.tenantSlug;
    if (hinted && hinted !== claims.tenant_slug) {
      this.audit.securityEvent('tenant_mismatch', { tenantId, hinted });
      throw new NotFoundException();      // 404, not 403 — see §8.4
    }

    const cfg = await this.tenants.get(tenantId);
    if (cfg.status !== 'active') throw new ForbiddenException('tenant_suspended');

    const ctx: TenantContext = {
      tenantId, tier: cfg.tier, userId: claims.sub,
      role: claims.role, holdSeconds: cfg.holdSeconds,
    };

    // 3 · Context and DB scoping established together, so they cannot diverge.
    return runWithTenant(ctx, () =>
      this.db.withTenantScope(ctx, () => next.handle()));
  }
}

12.2 The consumer path — no tenant claim at all

Consumer endpoints cannot use the interceptor above, because a consumer token deliberately carries no tenant. The tenant is derived from the resource instead, and the two guards are mutually exclusive by design.

tenancy/consumer.guard.ts
@Injectable()
export class ConsumerGuard implements CanActivate {
  async canActivate(ctx: ExecutionContext) {
    const req = ctx.switchToHttp().getRequest();
    const claims = req.user;             // may be undefined — guests are fine

    // A STAFF token here is an error, not a convenience. It would let a
    // Nyati clerk transact as a customer of Prestige. Fail loudly.
    if (claims?.tenant_id) {
      this.audit.securityEvent('wrong_token_type', { path: req.path });
      throw new ForbiddenException('wrong_token_type');
    }

    // Guests have no identity at all. That is allowed — ownership is
    // proved by the signed hold token, not by who you are.
    req.consumerId = claims?.sub ?? null;
    return true;
  }
}
inventory/hold.controller.ts — where the tenant actually comes from
@UseGuards(ConsumerGuard)
@Post('screenings/:id/holds')
async createHold(@Param('id') screeningId: string, @Body() dto: HoldDto) {
  // The caller supplied an object id. WE supply the tenant, by looking
  // it up. At no point is the caller's opinion of the tenant consulted.
  const screening = await this.catalogue.findPublicScreening(screeningId);
  if (!screening) throw new NotFoundException();

  const cfg = await this.tenants.get(screening.tenantId);
  const ctx = toSystemContext(cfg);        // tenant context, no user

  return runWithTenant(ctx, () =>
    this.db.withTenantScope(ctx, () =>
      this.holds.acquire(screeningId, dto.seatIds)));
}
Why this is not “trusting the URL”

Chapter 6 of the masterclass forbids taking the tenant from the request. This does not: the caller supplies screeningId, an object identifier, and the server derives the tenant from its own row. What would be forbidden is accepting a tenant_id supplied alongside it — and note there is nowhere in this handler for such a value to enter.

Below this line, everything is identical to the staff path: the same runWithTenant, the same SET LOCAL, the same RLS. Only the way the tenant was established differs.

12.3 Data access and isolation

The provider resolves pooled versus siloed placement and issues SET LOCAL inside the transaction. This is the only place in the system that knows a tenant may live in a different database.

tenancy/tenant-db.provider.ts
@Injectable()
export class TenantDb {
  private pools = new Map<string, Pool>();

  /** Pooled tenants share the default pool; siloed tenants get their own.
    * Application code never learns which it received. */
  private poolFor(cfg: TenantConfig): Pool {
    const ref = cfg.dbRef ?? '__pooled__';
    if (!this.pools.has(ref)) this.pools.set(ref, createPool(ref));
    return this.pools.get(ref)!;
  }

  async withTenantScope<T>(ctx: TenantContext, fn: () => Promise<T>) {
    const client = await this.poolFor(await this.cfg(ctx)).connect();
    try {
      await client.query('BEGIN');
      // SET LOCAL — scoped to this transaction. A plain SET would leak
      // this tenant's id onto the pooled connection for the NEXT request.
      await client.query('SET LOCAL app.tenant_id = $1', [ctx.tenantId]);
      const result = await withClient(client, fn);
      await client.query('COMMIT');
      return result;
    } catch (e) {
      await client.query('ROLLBACK'); throw e;
    } finally { client.release(); }
  }
}
Two mistakes to guard against in review

A second pool that bypasses this provider. Any module that creates its own connection escapes SET LOCAL, and its queries will see either nothing or — if it connects as a privileged role — everything. Enforce a single connection path with a lint rule.

Handlers that mention tenantId. If business logic ever writes where(eq(booking.tenantId, …)), the boundary has moved back into application code. RLS already does this. A handler mentioning tenant scoping is a signal that someone does not trust the mechanism — resolve the doubt rather than duplicating the filter.

12.4 The hold service

inventory/hold.service.ts
@Injectable()
export class HoldService {
  // Registered once at boot; Redis executes it atomically.
  private readonly ACQUIRE = `
    for i = 1, #KEYS do
      if redis.call('EXISTS', KEYS[i]) == 1 then return {0, i} end
    end
    for i = 1, #KEYS do
      redis.call('SET', KEYS[i], ARGV[1], 'NX', 'EX', ARGV[2])
    end
    return {1, 0}`;

  private key(t: TenantId, scr: string, seat: string) {
    return `lock:t:${t}:scr:${scr}:seat:${seat}`;   // tenant first
  }

  async acquire(screeningId: string, seatIds: string[]) {
    const ctx = currentTenant();
    if (seatIds.length > ctx.maxSeats) throw new BadRequestException();

    const holdId = randomUUID();
    const keys = seatIds.map(s => this.key(ctx.tenantId, screeningId, s));

    // 1 · Atomic across all seats — all or nothing.
    const [ok, failedIdx] = await this.redis.eval(
      this.ACQUIRE, keys.length, ...keys, holdId, ctx.holdSeconds);

    if (!ok) throw new ConflictException({
      error: 'seats_unavailable',
      unavailable_seat_ids: [seatIds[failedIdx - 1]],
    });

    const expiresAt = new Date(Date.now() + ctx.holdSeconds * 1000);
    try {
      // 2 · Durable record. ON CONFLICT is the belt to Redis's braces:
      //     if Redis ever lets two winners through, Postgres will not.
      await db.insert(seatLock).values(seatIds.map(seatId => ({
        screeningId, seatId, tenantId: ctx.tenantId,
        status: 'held' as const, holdId, expiresAt,
      }))).onConflictDoNothing();
    } catch (e) {
      await this.redis.del(...keys);   // don't strand the seats
      throw e;
    }
    return { holdId, expiresAt, seconds: ctx.holdSeconds };
  }
}

12.5 Converting a hold to a booking

The ordering here is deliberate and is the answer to the failure mode in §7.4. Note especially that payment is refused when the hold is nearly dead, and that a charge against a lost hold refunds itself.

booking/booking.service.ts — abbreviated
async confirm(holdId: string, payment: PaymentInput, idempotencyKey: string) {
  const ctx = currentTenant();

  // 1 · Refuse to start paying if the hold may die mid-flight.
  const ttl = await this.holds.ttlFor(holdId);
  if (ttl < 45) throw new GoneException({ error: 'hold_expired' });

  // 2 · Charge. Idempotency key = hold id, so a retry never charges twice.
  const charge = await this.payments.capture({
    ...payment, idempotencyKey: idempotencyKey ?? holdId,
  });

  // 3 · Re-verify AFTER capture. This is the window §7.4 is about.
  if (!await this.holds.stillOwned(holdId)) {
    await this.payments.refund(charge.id, 'seats_lost');
    this.metrics.inc('booking.seats_lost_after_capture', { tenant: ctx.tenantId });
    throw new PaymentRequiredException({
      error: 'seats_lost_payment_refunded', refund_reference: charge.id,
    });
  }

  // 4 · One transaction: lock → sold, booking, tickets. All or nothing.
  const booking = await db.transaction(async tx => {
    const updated = await tx.update(seatLock)
      .set({ status: 'sold', expiresAt: null, bookingId })
      .where(and(eq(seatLock.holdId, holdId), eq(seatLock.status, 'held')))
      .returning();
    // If another process changed these rows, updated.length will not match.
    if (updated.length !== seatCount) tx.rollback();
    return createBookingAndTickets(tx, updated, charge);
  });

  // 5 · Redis has served its purpose; Postgres is now the record.
  await this.holds.release(holdId);
  this.events.emit('booking.confirmed', { tenantId: ctx.tenantId, booking });
  return booking;
}

12.6 Background workers

Workers have no request, therefore no ambient context

This is the most common place for tenant isolation to fail in a NestJS system. A BullMQ processor runs outside any HTTP request, so AsyncLocalStorage is empty and currentTenant() throws — which is the correct, fail-closed behaviour. Every job payload must therefore carry its tenantId, and every processor must open a tenant scope explicitly as its first action.

Worker pattern — apply to every processor without exception
@Processor('notifications')
export class NotificationProcessor {
  async process(job: Job<{ tenantId: TenantId; bookingId: string }>) {
    const cfg = await this.tenants.get(job.data.tenantId);

    // Establish context from the payload, exactly as the interceptor
    // does from the token. Everything below is then tenant-scoped.
    return runWithTenant(toContext(cfg, 'system'), () =>
      this.db.withTenantScope(ctx, async () => {
        const booking = await db.query.booking.findFirst({
          where: eq(booking.id, job.data.bookingId),   // RLS scopes it
        });
        await this.sms.send(booking);
      }));
  }
}

The sweeper of §7.5 is the deliberate exception: it runs platform-wide with an elevated role and no tenant scope. There are exactly two such jobs in the system — the sweeper and the metering aggregator — and both are marked in code, reviewed as security-sensitive, and covered by tests asserting they touch nothing else.
