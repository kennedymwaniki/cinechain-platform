10.1 Service decomposition

ServicesG ch. 7, “Designing Multi-Tenant Services”, p. 158 are separated along failure-domain lines rather than by data entity. The question asked of each boundary was “if this fails, what else should keep working?”

A word on starting with a modular monolith

Nothing in this document requires seven separately deployed services on day one. A single deployable with seven clearly bounded modules — separate schemas of ownership, no cross-module database access, communication through interfaces — will serve the first two hundred tenants comfortably and is substantially easier to operate with a small team.

What matters is that the boundaries are real from the start, so that extracting Inventory into its own service when it needs independent scaling is a deployment change rather than an archaeology project. Draw the lines early; defer the network calls.

The constraint that keeps four tiers affordable

There is no if (tier === 'premium') in business logic anywhere in this system. Tier differences are expressed exclusively as: limits read from tenant configuration, a connection string resolved per request, and infrastructure policy applied outside the application.

Adding a fifth tier should require a configuration row and a pricing page. If it ever requires a sprint, tier logic has leaked into business logic and should be refactored out before it spreads.

10.3 Cluster topology

Promoting a tenant from pooled to siloedAzure SQL — SaaS tenancy patterns

This must be a supported operation rather than a project, because it is how the commercial model works. The sequence:

  1. Provision the tenant's dedicated database and apply the identical schema migration set.
  2. Copy their rows with logical replication, filtered by tenant_id, and let it catch up.
  3. Place the tenant in a brief read-only window — target under 60 seconds, scheduled outside trading hours.
  4. Verify row counts and checksums per table between source and target.
  5. Update tenant.db_ref; new requests resolve to the new database from the next connection.
  6. Lift read-only. Retain the source rows for a defined period, then delete them.

Steps 4 and 6 are the ones teams skip and later regret. Verification before cutover is what makes the operation reversible; retention after cutover is what makes rollback possible if a problem appears an hour later.

10.4 Handling the blockbuster peak

The defining load event for this system is a single tenant releasing tickets for a major opening. Five mechanisms combine, and none is sufficient alone:

  • Per-tenant rate limits at ingress.G ch. 14, “Throttling and Tenant Experience”, p. 381 Nyati may burst well above their steady-state allowance, but not without bound. This is the primary protection for every other tenant.
  • Autoscaling on the Inventory service first. It absorbs seat-map reads and hold attempts, which is where the load actually lands.
  • Seat-map reads served from Redis, never from PostgreSQL, during a sale. The database sees writes, not the read storm.
  • Separate connection pools per service, so that a reporting query cannot exhaust the connections Booking needs.
  • A documented pre-scale procedure. Major on-sales are known days in advance — the chain schedules them. Scaling up ahead of a known peak is not an admission of failure; it is the cheapest available mitigation.

If, despite these, one tenant's peaks routinely degrade others, the answer is the bridge model: move that tenant to Premium, give them a dedicated database, and charge for it. That is not a workaround — it is the architecture working as designed.
